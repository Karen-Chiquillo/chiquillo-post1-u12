# ADR-001: Capas simples para la persistencia; el seam de notificación ya cubre el próximo cambio conocido

## Estado

Aceptado — 2026-10-31

## Contexto

El sistema de solicitudes de reembolso ya integra Chain of Responsibility (validación), Strategy (cálculo por categoría) y Observer (notificación). Falta decidir si se migra a arquitectura Hexagonal completa, con un puerto por cada dependencia externa, o si se mantiene en capas simples. La Guía (sección 6.2) da el criterio: Hexagonal vale la pena "en sistemas que sobrevivirán 3 años o más con cambios de infraestructura". Ese criterio se evalúa por separado para las dos dependencias externas que tiene el sistema, con datos del propio código:

**Persistencia.**
- Hay un solo motor (H2 con Spring Data JPA) y ningún plan de cambiarlo.
- `RepositorioSolicitudesJpa` lo usa una sola clase, `SolicitudReembolsoService`, con tres métodos: `findByEmpleadoIdAndEstado`, `findById` y `save`.
- El beneficio principal que se le atribuye a Hexagonal, un dominio sin JPA, ya existe: el mapeo está en `META-INF/orm.xml` y `dominio/` no importa ni Spring ni JPA. Spring Data solo aparece en `infraestructura/`.

**Notificación.**
- Contabilidad anunció para el próximo trimestre una integración por API externa para programar el pago de las solicitudes aprobadas. Es el único cambio de infraestructura con fecha conocida.
- El servicio no conoce a ningún notificador concreto: recibe una `List<ObservadorCambioEstado>`. Ninguna otra clase del proyecto referencia a `NotificadorContabilidad`.

## Alternativas evaluadas

| Alternativa | Persistencia | Notificación | Costo |
|-------------|--------------|--------------|-------|
| **A. No cambiar nada (capas simples)** | El servicio sigue dependiendo de `RepositorioSolicitudesJpa`. | `ObservadorCambioEstado` sigue siendo el punto de extensión. | Ninguno. |
| B. Puerto solo para persistencia | Interfaz `RepositorioSolicitudes` en el dominio + adaptador JPA que la implementa y delega en Spring Data. | Igual que A. | 1 interfaz + 1 adaptador que solo reenvía 3 métodos. |
| C. Hexagonal completa | Igual que B. | Además, un puerto propio para pagos (`ProgramadorPagos`) y casos de uso como puertos de entrada. | 4 o más tipos nuevos, y el `SolicitudReembolsoService` actual partido en casos de uso. |

## Decisión

Se decide la **alternativa A**.

- **Persistencia:** `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`, sin un puerto intermedio. Hoy no se cumple el criterio de la Guía: no hay un cambio de motor previsto, y el aislamiento del dominio, que es lo que justificaría el puerto, ya se consiguió con `orm.xml`. Un puerto con un único adaptador que reenvía tres métodos sería una interfaz con un solo implementador, que la Guía (sección 4.1) señala como sobreingeniería (YAGNI).
- **Notificación:** no se cambia la estructura. Aquí sí hay un cambio de infraestructura con fecha, pero `ObservadorCambioEstado` ya cumple el papel de puerto: cuando llegue la API de Contabilidad, solo cambia el interior de `NotificadorContabilidad`, sin tocar `SolicitudReembolsoService` ni los otros dos observadores. Un puerto `ProgramadorPagos` encima de eso sería una segunda abstracción para el mismo cambio.

## Consecuencias

**Positivas:**
- No se agregan interfaces ni adaptadores de persistencia sin un caso de uso que los justifique.
- El único cambio de infraestructura con fecha (la integración de Contabilidad) ya tiene su punto de extensión, y afecta a una sola clase.
- El dominio sigue siendo Java puro, que era la razón principal para considerar Hexagonal, sin pagar el costo de los puertos.

**Negativas:**
- Si en el futuro se cambia de motor de base de datos, el puerto de persistencia tendrá que introducirse después y modificar `SolicitudReembolsoService`. Se acepta esa deuda técnica de forma consciente (deliberada y prudente, en el cuadrante de la Unidad 10).
- `SolicitudReembolsoService` no se puede probar con un repositorio falso escrito a mano; sus pruebas pasan por `@SpringBootTest` con H2, que tarda unos segundos en lugar de milisegundos.
- Los observadores se ejecutan dentro de la transacción de `cambiarEstado` (`@Transactional`). Hoy solo escriben en el log, pero cuando `NotificadorContabilidad` llame a la API externa, una falla de esa API revertiría el cambio de estado después de que Auditoría ya registró el cambio (en la ejecución actual Auditoría corre primero, y Spring no garantiza ese orden sin `@Order`). Esto **no** exige un puerto nuevo, pero sí una condición para la integración: Contabilidad tendrá que reaccionar después del commit (por ejemplo con `@TransactionalEventListener(phase = AFTER_COMMIT)` o `TransactionSynchronization`), de modo que una falla externa no deshaga una decisión ya tomada.
- Un revisor que espere simetría (puertos en todas las dependencias externas) puede leer la asimetría como inconsistencia si no lee este ADR.

## Señales para revisar esta decisión

- Aparece un segundo motor de persistencia (por ejemplo, una réplica de lectura en otra tecnología) o un plan concreto de migración: introducir el puerto `RepositorioSolicitudes` (alternativa B).
- Las pruebas del servicio se vuelven lentas o frágiles por depender de H2: un repositorio falso detrás de un puerto pasaría a tener un beneficio medible.
- Llega la integración de Contabilidad: aplicar la condición de ejecutar después del commit descrita en las consecuencias.
